# T-01｜细粒材料实验室技术基线

状态：实现基线 v0.1
更新：2026-08-06

## 1. 目标

首个可运行切片只验证四件事：材料可在任意位置被改变；水、沙、热、冷、燃烧、相变、碎裂与浮动能形成可读因果；单词咒语只输入物质、热量或力；暗色竖向洞窟在桌面与手机浏览器中保持可操作。

这不是完整战斗关卡，也不承诺最终引擎。实验室代码必须允许以后替换材料模拟内核，而不重写语言解析、任务数据或界面。

## 2. 技术选择

- 产品表面：浏览器/PWA 优先。
- 灰盒：Vite、TypeScript、Canvas 2D `ImageData`。
- 逻辑画布：`270×480`，显示时最近邻放大。
- MVP 物理格：`2×2` 逻辑像素，即 `135×240 = 32,400` 格。
- 目标物理格：`1×1` 逻辑像素，即一屏 `129,600` 格。
- 模拟：固定 30 Hz；渲染与输入目标 60 FPS。
- 数据布局：类型化数组；不为材料格创建 DOM、精灵或游戏对象。
- 并行边界：首版在主线程验证；达到 `1×1` 或出现长时帧后迁移到 Web Worker，随后再依据剖析决定是否使用 Rust/WASM。

不在首版引入 Godot。原因不是 Godot 不能制作 2D RPG，而是本项目首先需要浏览器原生的数据驱动语言界面和可替换材料内核；先用更小的静态 Web 交付面验证材料循环，可以避免同时承担通用引擎 Web 导出、线程、扩展和资源体积约束。

## 3. 材料格契约

当前运行时数组：

```text
material: Uint8
temperature: Int16（0.1°C）
integrity: Uint8
phaseProgress: Uint8
burning: Uint8
lift: Uint8
movedAt: Uint32
```

正式内核将把静态材料参数移入只读表，并为动态格按需增加速度、浓度、电荷和反应进度 sidecar。所有状态转换必须由物理事件产生，不允许动画直接改写世界。

## 4. MVP 现象

| 现象 | 当前最小实现 | 后续替换点 |
|---|---|---|
| 水流 | 下落、斜落、横向找空位 | 体积、压力、静止水段压缩 |
| 沙与灰 | 下落、沿斜面滑动 | 安息角、休眠与重唤醒 |
| 加热/冷却 | 圆形热量输入和简化导热 | 热焓、潜热与材料导热率 |
| 燃烧 | 木材达到燃点后持续耗损并加热邻格 | 湿度、氧暴露、阴燃与烟 |
| 冻结/融化 | 阈值与相变进度 | 晶核、潜热和体积变化 |
| 蒸发/凝结 | 水与蒸汽互转 | 露点、压力与气体浓度 |
| 震碎/爆炸 | 距离衰减的损伤与热输入 | 遮挡、压力波和碎片冲量 |
| 浮动 | 局部上升力改变水和粉体运动 | 统一力场、刚体浮力和 MP 维持 |

## 5. 语言边界

实验室开放的单词共鸣是 `telo`、`seli`、`lete`、`kiwen`、`ko`、`kon`。它们分别输入少量物质、热量、冷却或力，不直接编码伤害技能。

“实验震碎”是开发工具，不是 `pakala` 的单词魔法。界面必须持续标明这一边界，避免把调试操作误教为正式语言能力。

## 6. 性能门槛

第一轮验收目标：

- 桌面 Chromium：持续 60 FPS，模拟 30 Hz。
- 中端手机：渲染不低于 45 FPS，模拟保持 20–30 Hz。
- 单次普通施法不产生超过 50 ms 的主线程长任务。
- 重置场景后材料状态、MP 与玩家位置确定性恢复。
- 物理结果只依赖固定状态、输入、版本和随机种子。

性能不足时依次降低：离屏活跃范围、热/气体频率、视觉粒子数量、液体更新频率；最后才退回更粗的物理格。

## 8. 已知未知

- `1×1` 物理格在移动端是否能保持目标更新率。
- Canvas 2D 动态上传何时需要替换为 WebGL/WebGPU 纹理。
- 模拟线程与主线程之间采用复制缓冲、Transferable 还是跨域隔离后的共享内存。
- RPG 碰撞轮廓应从材料格合并矩形，还是保持独立粗碰撞网格。
- 角色种族的形变与流体交互是否需要独立软体求解器。
